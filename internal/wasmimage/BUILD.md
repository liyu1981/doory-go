# Embedded image encoders

`webp-1.6.0.wasm` and `jpeg-turbo-3.1.0.wasm` are the two encoder modules the
Go binary embeds. They are **committed** so a release build needs no C
toolchain, emscripten, wasi-sdk or Docker.

The Go wrappers call a tiny exported C ABI; there is no child process:

| module | target | exports | used by |
|---|---|---|---|
| `webp-1.6.0.wasm` | libwebp 1.6.0 | `doory_webp_encode`, `doory_webp_free` | `doory.encodeWebPQuality` |
| `jpeg-turbo-3.1.0.wasm` | libjpeg-turbo 3.1.0 (JPEG API 6.2) | `doory_jpeg_encode` | `doory.encodeJPEG`, `doory.convertImage` |

Pillow 13.0.0 (the pinned oracle) links libwebp 1.6.0 and libjpeg API 6.2, so
the wrappers mirror Pillow's encoder contract:

- WebP: `quality`, `method=4`, `lossless`, `alpha_quality=100`, `exact=0`
  (`PIL.WebPImagePlugin._save`).
- JPEG: `jpeg_set_quality(..., TRUE)`, `optimize_coding`, optional
  `jpeg_simple_progression` (`PIL.JpegImagePlugin._save` with
  `optimize=True`).

`internal/wasmimage/wasmimage_test.go` compares the output byte-for-byte with
fixtures generated by the oracle, so a change in either module fails loudly.

## Reproducing the modules

Build both in a wasi-sdk 24 container from the pinned release archives:

```sh
mkdir -p /tmp/wasm-enc && cd /tmp/wasm-enc
curl -fsSLO https://storage.googleapis.com/downloads.webmproject.org/releases/webp/libwebp-1.6.0.tar.gz
curl -fsSL -o libjpeg-turbo.tar.gz https://github.com/libjpeg-turbo/libjpeg-turbo/archive/refs/tags/3.1.0.tar.gz
tar xzf libwebp-1.6.0.tar.gz
tar xzf libjpeg-turbo.tar.gz
cp -r /path/to/doory-go/internal/wasmimage/src wrappers
```

```sh
docker run --rm -v /tmp/wasm-enc:/work -w /work ghcr.io/webassembly/wasi-sdk:wasi-sdk-24 bash -lc '
set -euxo pipefail
cmake -S libwebp-1.6.0 -B build-webp \
  -DCMAKE_TOOLCHAIN_FILE=/opt/wasi-sdk/share/cmake/wasi-sdk.cmake \
  -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF \
  -DWEBP_ENABLE_SIMD=OFF -DWEBP_BUILD_CWEBP=OFF -DWEBP_BUILD_DWEBP=OFF \
  -DWEBP_BUILD_GIF2WEBP=OFF -DWEBP_BUILD_IMG2WEBP=OFF -DWEBP_BUILD_VWEBP=OFF \
  -DWEBP_BUILD_WEBPINFO=OFF -DWEBP_BUILD_WEBPMUX=OFF -DWEBP_BUILD_EXTRAS=OFF \
  -DWEBP_BUILD_LIBWEBPMUX=OFF -DWEBP_BUILD_LIBWEBPDEMUX=OFF \
  -DCMAKE_C_FLAGS=-O3
cmake --build build-webp --target webp -j4

cmake -S libjpeg-turbo-3.1.0 -B build-jpeg \
  -DCMAKE_TOOLCHAIN_FILE=/opt/wasi-sdk/share/cmake/wasi-sdk.cmake \
  -DCMAKE_BUILD_TYPE=Release -DENABLE_SHARED=0 -DWITH_TURBOJPEG=0 \
  -DWITH_SIMD=0 -DPNG_SUPPORTED=0 -DWITH_TOOLS=0 \
  -DCMAKE_C_FLAGS=-O3
cmake --build build-jpeg --target jpeg-static -j4

/opt/wasi-sdk/bin/clang --target=wasm32-wasi -mexec-model=reactor -O3 \
  -Ilibwebp-1.6.0/src -o webp.wasm wrappers/webp.c \
  build-webp/libwebp.a build-webp/libsharpyuv.a -lm -Wl,--export-dynamic

/opt/wasi-sdk/bin/clang --target=wasm32-wasi -mexec-model=reactor -O3 \
  -Ilibjpeg-turbo-3.1.0/src -Ibuild-jpeg -o jpeg.wasm wrappers/jpeg.c \
  build-jpeg/libjpeg.a -lm -Wl,--export-dynamic
'
```

`-mexec-model=reactor` matters: without it the WASI crt exports `_start`,
which runs the (empty) command main on instantiation and traps under wazero.

Copy the two files back and update the hashes below.
